# Internationalization

## Language rules

- Supported locales: `zh` (Simplified Chinese), `en` (English).
- Public page URLs are authoritative: `/`, `/marketplace`, `/patterns/:id`, `/guides/...` are Chinese; `/en`, `/en/marketplace`, `/en/patterns/:id`, `/en/guides/...` are English.
- Public pages do not redirect based on browser headers or localStorage. A shared URL always returns the same language, including with JavaScript disabled.
- Public language links retain the current page and its query parameters. Source images and `/api` URLs are not language-prefixed.
- The editor uses `/editor` and `/en/editor`. Switching languages updates the interface and URL without remounting the canvas. The legacy localStorage key `perler-beads-generator:language` is preserved; visiting the old `/editor` entry with an English preference redirects to `/en/editor`.
- Drafts, favorites, login cookies, color codes, database category values and user content are shared between locales. Titles, creator names and descriptions are not machine-translated.

## Where translations live

- `shared/i18n/messages.json`: common UI, accounts, statistics, marketplace, error messages and named interpolation. Each namespace has the same keys and parameter names in both languages.
- `shared/i18n/pages.zh.json` / `pages.en.json`: developer-authored public page titles, descriptions and HTML. This is trusted repository content; never insert user-generated HTML here.
- `src/editorMessages.tsx`: editor-specific labels and existing rich React / function translations, extracted from App. TypeScript checks editor and tool key coverage in both languages.
- `src/i18n.ts`: typed `t`, reactive `useLocale`, URL generation, dates, numbers and category display helpers.
- `shared/i18n/runtime.cjs`: server translation helpers using the same message catalog.
- `server/localize-errors.cjs` / `shared/i18n/error-keys.json`: map existing server validation errors to stable codes and localized public messages. API clients send Accept-Language; server defaults to Chinese and respects supported language quality values.

The build writes `/i18n.js` from the shared catalog before loading app modules. Both server HTML and browser interactions use the same translated strings. No extra runtime package is required.

## Adding or changing text

1. Add the same semantic key to `messages.zh` and `messages.en`; prefer complete sentences over assembling translated fragments.
2. Use named parameters, for example `t('account.days', { count: 7 })`. React escapes UI text; server templates must explicitly HTML-escape user data, including values interpolated into attributes and metadata.
3. Where plural forms differ, add a `.one` or `.other` variant. `Intl.PluralRules` chooses an available variant, then falls back to the base key. Chinese is the fallback language; unknown keys remain visible as keys for diagnosis.
4. Use `localePath` for navigation, `categoryLabel` only for category display, `formatDate` and `formatNumber` for locale-aware values. Keep category option values unchanged for the existing database schema.
5. Run `npm run check:i18n`, `npm test`, and `npm run build`. The build rejects missing translations or interpolation mismatches. TypeScript rejects unknown frontend message keys.

## SEO and deployment

Public language variants are built / rendered separately with self canonical URLs, reciprocal `hreflang` links (`zh-CN`, `en`, `x-default`), matching HTML lang and OG locale. Sitemap lists both versions. The editor remains noindex. Vercel and the local server support the English routes. Existing Chinese links and old hash shares remain compatible. No database migration is required.
